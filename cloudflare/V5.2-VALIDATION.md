# v5.2 開發驗證（2026-10-30）

基準：PR #4，`cb7addac94b7fe180b9c0e3a8ff355fff7dae37d`。

本輪僅修改開發分支的背景模組、離線合併器與測試；沒有連線至正式 Cloudflare、修改 D1、執行部署或合併 main。原聊天與記憶的程式及資料均未操作。

## 已修正並驗證

- Spotify token 與 player 的 429 均遵守 Retry-After，不再把超過一天的等待截短。等待期間不再查詢。
- 授權失效時停用背景查詢並刪除已保存的加密 refresh token。
- 訂閱先驗證 P-256 曲線點、16-byte auth secret、HTTPS 標準連接埠；發送禁止重新導向。
- 合併結果保留原 Worker 其他可列舉屬性及事件處理器（例如 queue），並保留原 fetch 與 scheduled 呼叫。

執行 `node --test cloudflare/background.test.mjs cloudflare/concurrency.test.mjs cloudflare/frontend.test.mjs cloudflare/merge-engine.test.mjs cloudflare/merge-offline.test.mjs`：27 項通過。

新增測試涵蓋 refresh token 輪替後加密保存與再次使用、204、兩個端點的 429、失效授權、無效訂閱、接收端 ECDH/HKDF/AES-GCM 解密、VAPID audience/期限/簽章，以及 410 清除訂閱。HKDF 接收端使用 Node 原生實作，與發送端 WebCrypto 實作分開驗證。所有網路回應與 D1 都是測試替身。

## 第二輪完善

- 使用獨立背景表 `ling_v4_jobs` 的原子 SQL 執行鎖，90 秒到期可恢復，finally 只釋放自己的鎖。Spotify 網路請求各限時 10 秒。
- 背景寫入以加密授權快照作為 SQL 條件；停用或重新授權後，舊請求不能重建 token、歌曲狀態或覆寫新的授權。
- 新增 6 項記憶體 SQLite 測試，實際執行 SQL，涵蓋重疊 Cron、例外釋放鎖、過期鎖恢復、refresh/player 等待時停用、重新授權與失效回應的競態，以及既有聊天與記憶表不變。
- 前端防止重複操作，保留點擊當下的通知權限請求，狀態刷新不再蓋掉成功提示。網路及服務工作者等待都有逾時處理。
- 最多 12 個推播並行發送，各自限時 10 秒，單一裝置失敗不阻塞其他裝置。
- 合併器改為引用未修改的 `worker.original.mjs`，保留原模組的具名匯出，其他事件函式綁定原 Worker，避免文字替換及命名衝突。
- `merge-live.mjs` 移除固定正式 Worker/D1 資源及 Wrangler 部署設定產生；唯讀稽核必須明確指定 Worker 名稱。所有產物只可作審查預覽。
- `merge-offline.mjs` 可處理既有私有稽核原始碼；先檢查語法，再輸出原始模組、包裝模組與雜湊摘要，拒絕覆寫。產物已加入 `.gitignore`。

## 尚未驗證

- 真實 iPhone 主畫面 App 的訂閱與通知送達。
- 正式 Worker 真實原始碼的合併、全部事件與設定相容性；目前僅有合成 Worker 測試，入口辨識仍採保守規則，需要人工審核與獨立環境驗證。
- Cloudflare D1 分散式環境行為。本機 SQLite 驗證 SQL 與可控競態，並不等同正式 D1 整合測試。
- 授權關閉前已送出的 Spotify HTTP 或推播不能撤回；執行鎖是有期限的租約，不宣稱所有故障情境都能 exactly-once。

下一階段需取得既有唯讀稽核原始碼與設定快照，在離線或獨立測試環境驗證；不得以目前測試通過作為正式部署依據。

規格依據：[RFC 8291](https://datatracker.ietf.org/doc/html/rfc8291)、[Spotify Rate Limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits)、[Refresh token expiration](https://developer.spotify.com/blog/2026-06-18-refresh-token-expiration)。
